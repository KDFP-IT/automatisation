# Подбор норм ГЭСН по позициям ВОР — отчёт о работе

Дата: 23–24 ноября 2026. Ветка: `fix/vps-hotfixes`. VPS: `vor-smeta` (`192.168.30.183`).

## 1. Условия задачи

Сметчица работает только в Open WebUI: прикрепляет `ВОР.xlsx`, просит подобрать нормы ГЭСН на каждую позицию — до 3 кандидатов с объяснением различий и пометками, где данных не хватает. На выходе — таблица в чате + итоговый XLSX.

Ключевые требования из постановки:

- Обрабатывать **все строки** ведомости, а не несколько совпадений.
- Названия работ и норм могут **вообще не совпадать** («уложить щебень» vs «устройство основания»).
- Окончательный выбор нельзя делать по текстовому сходству: проверять технологию, материалы, состав работ, условия, измеритель (подход Минстроя).
- Одна позиция ВОР ≠ одна норма: возможны покрытие несколькими нормами, вложенность, двойной учёт.
- ГЭСН — ресурсные нормы, не цены: подбор — первый этап, смета с ценами (ГРАНД-Смета) — отдельно.
- Задел на будущее: аналогичная логика понадобится электрикам (ГЭСНм) — архитектура должна масштабироваться без нового сервиса.

Исходные данные: архив `ФСНБ-2022 (приказ Минстроя №727пр).zip` (7.3 МБ → 172 МБ), pilot-файлы с сетевого диска K: ВОР `006_26 ... ВР-1/ТКР3 (Трамв. пути).xlsx` (64 позиций после парсинга) и ЛСР `006_25 ... 01-03-01 ...xlsx` (ГРАНД-Смета, 28 позиций с шифрами — эталон).

## 2. Сделанная архитектура

```
Сметчица: ВОР.xlsx в чате Open WebUI (vor-smeta:8080)
  → Tool kdfp_gesn (match_vor_to_gesn / list_editions, class Tools)
  → POST multipart + Bearer → Flask gesn-match (127.0.0.1:8101)
  → parse (openpyxl) → дедуп → детектор материалов
  → гибридный поиск (Postgres norms-db: FTS + trigram + pgvector → RRF)
  → reranker mmarco-mMiniLMv2 (30→5)
  → batch LLM-verify (6 позиций/вызов, 4 воркера, deepseek-v4.1-flash через RouterAI)
  → XLSX-отчёт + ссылка /api/v1/files/{id}/content в чат
```

### 2.1. Компоненты

| Компонент | Где | Что делает |
|---|---|---|
| `kdfp_gesn.py` | `~/open-webui/tools/` на VPS + запись в `webui.db.tool` | Тонкий Tool: файл из чата → байты → POST в сервис → poll → карточка + XLSX в чат |
| `apps/gesn-match/app.py` | Flask + waitress, job engine как в `apps/kac` | `POST /api/v1/match → 202`, `GET /api/v1/match/<id>`, `GET .../xlsx`, `GET /api/v1/editions`, `GET /api/health` |
| `apps/gesn-match/import_fsnb.py` | `lxml.iterparse` | Парсинг XML ИАС ЦС в таблицы, идемпотентный upsert |
| `apps/gesn-match/retrieval.py` | Один SQL | FTS (`tsvector russian` + `unaccent`) + `word_similarity` (pg_trgm) + `<=>` (pgvector), фьюжн — RRF k=60 |
| `apps/gesn-match/embed.py` | `intfloat/multilingual-e5-small` (384) + `cross-encoder/mmarco-mMiniLMv2` | backfill эмбеддингов, rerank 30→5 |
| `apps/gesn-match/profiles/{building,montage}.yaml` | Чек-листы verify | `building` (ГЭСН), `montage` (ГЭСНм: напряжение, сечение, способ прокладки) |
| `apps/gesn-match/eval_recall.py` | Метрика пилота | Recall@3 / top-1 по ЛСР-эталону |
| `norms-db` | `pgvector/pgvector:pg16`, отдельный compose-проект `gesn-deploy` | `norms` / `norm_resources` / `norm_embeddings`, PK `(code, collection, edition_id)` |
| `deploy/portal/` | compose, nginx-route, `[tools.gesn-match]` в access.toml | Проводка в портал (сервис пока вне боевого `portal`-проекта, см. п. 5) |

### 2.2. Почему так, а не иначе

- **Нативный Tool, а не Tool Server / MCP / Pipe.** На VPS нет Tool Server; MCP — read-модель без аплоада байтов; Pipe перехватывает все сообщения. `_chat_files` из `kdfp_audit.py` — канонический мост «файл → байты».
- **Flask, а не FastAPI.** В репо нет ни одного FastAPI; job engine, гарды и audit-хуки скопированы из `apps/kac` и `apps/bookmarks`.
- **Отдельный Postgres, а не SQLite / obs-db.** Нужен pgvector; образ `obs-db` не трогаем. Fallback на `sqlite-vec` не понадобился.
- **Парсинг XML, а не Docling / чанки в Knowledge Base.** ФСНБ — уже структурированные данные (шифр, состав работ, ресурсы, НР/СП, иерархия). Чанкинг разорвал бы норму и измеритель.
- **Гибрид + RRF, а не чистые эмбеддинги.** Эмбеддинг в одиночку топит лексику (масштаб несопоставим: cosine ~0.8 vs ts_rank ~0.02). Взвешенная сумма 0.35/0.25/0.40 заменена на RRF — калибровка не нужна.
- **`word_similarity`, а не `similarity`.** Обычные триграммы штрафуют длинные названия норм («Балластировка пути, стрелочных переводов…» проигрывала коротким).
- **Контекст объекта только в эмбеддинг.** Первая попытка сунуть «Переустройство трамвайных путей» во все ветви убила FTS (AND-семантика plainto_tsquery). Лексика — чистая позиция, семантика — с контекстом.
- **LLM проверяет, а не выбирает.** Промпт запрещает сочинять шифры; при нехватке данных — `clarify` + список недостающих атрибутов. Парсер толерантен: свой формат, формат модели, двойной JSON, обрезанный JSON (regex-сальваж), пустые ответы (ретраи с паузой → поштучный fallback).
- **Пакетная обработка.** Один вызов на 6 позиций, 4 воркера; дедуп идентичных строк; детектор материалов (ГОСТ/ТУ/фракции/марки/ЩМА/ЭБДК/БСТ/профили/соединители) — материалам норма не подбирается.
- **CPU-torch.** pip притащил CUDA на ~2.5 ГБ на машину без GPU → `torch==2.8.0+cpu` с CPU-индекса (образ 1.95 ГБ вместо ~5).

## 4. Результаты прогонов

### 4.1. Скорость (ВОР 64 строки, ТКР-3)

| Прогон | Время |
|---|---|
| По одной позиции, 1 воркер | ~40+ мин |
| Батчи ×6, 4 воркера, дедуп, пропуск материалов | **< 5 мин** |

Распределение 64 строк финального прогона: 33 — материалы (пропущены), 31 — работы.

### 4.2. Точность (эталон — 28 шифров из ЛСР сметчика)

| Замер | Recall@3 | Top-1 |
|---|---|---|
| Дословные формулировки ЛСР | **28/28** | 28/28 |
| Формулировки ВОР (10 смаппированных позиций) | **5/10** | 2/10 |

LLM-статусы финального прогона: 93× `clarify`, 0× `ok`, 0× `error_retry`. Примеры корректного поведения:

- «Разборка трамвайного пути, рельсы Р65» → кандидаты `32-04-002-10/11`, `32-12-001-06`; вердикт `clarify` с `missing: [группа грунта, ...]` — семья верная, атрибутов в ВР нет, не угадывает.
- «Основание из щебня 15 см» → кандидаты ПГС и асфальтогранулят отклонены (`reject` с обоснованием «не щебень»), позиция помечена на проверку сметчику.
- «Балластировка пути» → в топ-3 есть `32-03-001-03` (та же таблица, другой материал) — точный вариант недостижим без указания материала в ВР.

### 4.3. Диагностика промахов

- Короткие запросы («Балластировка пути») проигрывают длинным названиям в триграммах — частично лечится `word_similarity`, остаток — за счёт контекста объекта и LLM.
- `28-01-*` (ж/д) vs `32-04-*` (трамвай): лексически неразличимы без контекста — контекст добавлен в эмбеддинг и промпт.
- 0× `ok` за весь пилот: система консервативна. Это осознанно на данном этапе (лучше clarify, чем ложное подтверждение), калибровка `ok` — по мере накопления эталонов.
- Флейки RouterAI (пустые ответы): ретраи с паузой + поштучный fallback; в финальном прогоне 6 batch-фолбэков, все recovered, 0 `error_retry` в выдаче.

## 6. Что дальше

1. **Эталон пошире.** Нужна пара ВОР+ЛСР с полным покрытием (в текущей покрыто 10 из 31 рабочих строк) — тогда Recall@3 честный, калибруем веса/пороги.
